Présentation du projet

Ce projet noté de fin de module (R4.A.08 — Outils de la virtualisation) consistait à concevoir et déployer une infrastructure d'entreprise complète via Docker Compose, en un binôme, dans un délai de 3 heures. L'objectif était de démontrer notre capacité à orchestrer des services interdépendants en respectant des principes stricts d'isolation réseau et de haute disponibilité.

Durée : 3 heures (TP noté)  |  En binôme  |  Contrainte : déploiement en une seule commande, isolation réseau stricte, évaluation automatisée

Architecture déployée

L'infrastructure complète repose sur 3 réseaux isolés et 7 conteneurs aux rôles distincts :

net_public — Zone exposée

  • proxy_nginx — Reverse proxy, point d'entrée unique (ports 80/443)
  • web_app — Serveur Apache/PHP (Dockerfile custom)
  • keycloak_auth — Gestion des identités (SSO)
  • mail_test — Intercepteur SMTP Mailpit

net_db — Zone bases de données

  • mysql_master — Base principale (écritures)
  • mysql_slave — Réplique en lecture seule

net_auth — Zone authentification

  • postgres_keycloak — BDD dédiée à Keycloak

Ce que j'ai mis en place

  • Docker Compose multi-services : rédaction du fichier docker-compose.yml orchestrant 7 conteneurs avec leurs dépendances (depends_on), volumes et variables d'environnement via .env.
  • Reverse proxy Nginx : configuration du nginx.conf pour router le trafic entrant vers web_app sans exposer ce dernier directement sur le réseau hôte.
  • Dockerfile custom pour web_app : image PHP/Apache personnalisée avec les extensions nécessaires (PDO,…).
  • Réplication MySQL Master/Slave : configuration des fichiers master.cnf et slave.cnf, exécution des commandes docker exec pour lier les deux instances et valider la synchronisation en temps réel.
  • Keycloak + PostgreSQL : déploiement du service d'authentification SSO avec sa base dédiée, configuration des variables d'environnement (KC_DB, KC_DB_URL…) pour le lier à PostgreSQL.
  • Isolation réseau : chaque conteneur n'est connecté qu'aux réseaux strictement nécessaires à son fonctionnement, sans accès transversal non autorisé.
  • Documentation README.md : schéma des flux réseau, commande de déploiement unique, mode opératoire de la réplication MySQL.

Ce que j'ai appris

Ce projet m'a plongé dans la réalité des infrastructures modernes : conteneuriser des services, les faire communiquer de façon sécurisée et les orchestrer proprement avec un seul fichier de configuration est une compétence directement applicable en entreprise. Voir l'ensemble de la stack démarrer en une seule commande après des heures de configuration est une vraie satisfaction.

La réplication MySQL a été la partie la plus délicate : comprendre le mécanisme de binlog, configurer les deux instances pour qu'elles se reconnaissent et vérifier que la synchronisation fonctionne en temps réel m'ont demandé de lire attentivement la documentation officielle et de déboguer méthodiquement. C'est aussi ce projet qui m'a appris à vraiment lire les logs Docker pour comprendre ce qui se passe dans un conteneur.

Keycloak a introduit une dimension nouvelle : la gestion des identités et le SSO sont des sujets que je n'avais jamais abordés concrètement. Comprendre le flux d'authentification — redirection vers Keycloak, obtention d'un token, validation côté application — m'a donné une base solide pour appréhender la sécurité dans les architectures microservices.
